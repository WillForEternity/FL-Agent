# Development

## Repository layout

| Path | Contents |
|---|---|
| `fl-studio-mcp/` | The MCP server (Python, managed with uv): `src/fl_studio_mcp/` tools and utilities, `fl_controller/` script that runs inside FL, `tests/` |
| `dsp/` | JSFX scripts for the FL-Agent plugins |
| `patches/ysfx-flagent.patch` | FL-Agent's changes to ysfx (plugins and renderer) |
| `scripts/` | `install.sh`, `build-plugins.sh`, `save-ysfx-patch.sh`, `generate_tool_reference.py` |
| `examples/` | Scripts that build example FL projects |
| `docs/` | Documentation |
| `.claude/settings.json` | Project permissions for Claude Code (allows running the build script) |
| `vendor/ysfx/`, `bin/` | Generated by the build script; git-ignored |
| `docs-personal/`, `.local/` | Personal notes and local backups; git-ignored |

## Tests and lint

```bash
cd fl-studio-mcp
uv run pytest -q          # no FL Studio needed; script render tests need bin/flagent_render
uv run ruff check src tests ../scripts ../examples
```

CI (`.github/workflows/ci.yml`) runs lint, the tests, a shell syntax check and the tool-reference check on every push. Plugin builds need macOS and aren't in CI.

## Building the plugins

```bash
./scripts/build-plugins.sh [--clean] [--no-install]
```

1. **Fetches ysfx** at a pinned commit into `vendor/ysfx` and applies `patches/ysfx-flagent.patch` (skipped if a matching checkout exists; set `FLAGENT_YSFX_DIR` to build elsewhere).
2. **Picks a working macOS SDK:** the newest one that can link a test program. Some Command Line Tools releases default to an SDK their own linker rejects (`ld: tapi error: malformed file`).
3. **Configures and builds** the two VST3 plugins and `flagent_render` (log: `vendor/ysfx/build/build.log`).
4. **Verifies:** each plugin binary contains every FL-Agent feature marker and has a valid signature, and the renderer compiles a known script.
5. **Installs** by atomic rename into `~/Library/Audio/Plug-Ins/VST3/` and `bin/`, so a running FL Studio keeps the old binary until it restarts.

### Changing ysfx
`vendor/ysfx` isn't committed; the patch is. After editing files in `vendor/ysfx`:

```bash
./scripts/save-ysfx-patch.sh    # regenerates patches/ysfx-flagent.patch, including new files
./scripts/build-plugins.sh
```

Mark FL-Agent changes in ysfx sources with an "FL-Agent" comment. Real-time code must not allocate, lock or do file I/O on the audio thread.

## Adding or changing tools
- Tools live in `fl-studio-mcp/src/fl_studio_mcp/tools/<area>.py`, each module with a `register_<area>_tools(mcp)` function listed in `tools/__init__.py:register_all_tools`. Add new modules to `RELOAD_ORDER` in `reload.py` (a test enforces this).
- Commands that need FL's API go in the controller script, `fl_controller/device_FLStudioMCP.py`: add a branch to `dispatch_command` and a `handle_*` function. Install it with `./scripts/install.sh --controller-only` and restart FL Studio.
- Regenerate the tool reference: `uv run python ../scripts/generate_tool_reference.py` (a test fails if `docs/tools.md` is stale).
- During a session, `fl_reload_tools` applies tool-code edits without restarting the server.

Guidelines:
- Look up plugins, parameters and slots **by name**; indices vary between projects.
- **Verify by reading back** (the new channel exists, the parameter changed, the request file was consumed) rather than trusting a command was sent.
- Anything that closes or overwrites a project must go through the unsaved-changes guard in `tools/app.py`.
- Keep code testable without FL: put logic in plain functions and test them with fakes or monkeypatching.
